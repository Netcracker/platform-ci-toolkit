# Common Linter

This directory builds the common linter image. The image extends GitHub Super-Linter v9 with organization-wide defaults. Keep `README.md` and `docs/usage.md` in sync with behavior changes.

## Commands

Run from `linter/`:

```sh
make build                 # build the local linter image
make push                  # push the image to the registry
make lint                  # run the linter against the parent repository
```

## Layout

- `Dockerfile`: installs `make` on top of the official Super-Linter image so CI can run `make lint` inside the linter container. It does not install Maven or a JDK; language tests run in language-specific test images. It also copies the `skillcheck` binary from the public `ghcr.io/netcracker/skillcheck` image (pinned by digest), and copies baseline rules plus `run.sh`.
- `run.sh`: container entry point. Ensures `/tmp/lint` points to the repository (linking to `CI_PROJECT_DIR` or `GITHUB_WORKSPACE` when running in CI), copies baseline linter configs to a writable directory, overlays consumer rules from `/tmp/lint/prechecks/custom-liners/` when present, loads environment files (restores caller `DEFAULT_BRANCH` if set via docker/CI), runs Super-Linter, runs `skillcheck` when `SKILLCHECK_PATTERNS` is configured, and runs `run_helm_lint` (`helm lint` + `helm template` piped into `kubeconform -ignore-missing-schemas`) against every `Chart.yaml` found under `/tmp/lint`.
- `super-linter.env`: baseline environment for Super-Linter. Disables languages that are not commonly used; excludes the Go module cache (`^\.go/pkg/mod/.*`) from linting; Go is left enabled so Super-Linter runs `GO` / `GO_MODULES`.
- `prechecks/base-linters/`: default rule files only for the enabled linters (golangci-lint, yamllint, ruff, Checkstyle, hadolint). Markdown uses the Super-Linter default. `.ruff.toml` (ruff) and `.checkstyle.xml` (Checkstyle, selected by `JAVA_FILE_NAME` in `super-linter.env`).
- `agent-packages/common-linter-integration/`: APM package with the `integrate-common-linter` skill (GitHub Actions and GitLab CI references) that guides AI agents when adopting the linter in a consumer repository. Keep it in sync with `docs/usage.md` and `templates/common.mk`.
- `templates/common.mk`: consumer Makefile template. Copy it into consumer repositories as `Makefile`, or include it from a thin wrapper. It provides `verify`, `test`, `test-go`, `test-python`, and `test-java` targets. `lint` delegates to `lint-super-linter`, `skill-validate`, and `lint-helm`; `verify` runs lint and tests; `test-go` auto-detects Go modules and runs tests in every module that has tests; `test-go`, `test-python`, and `test-java` skip when no relevant files changed against `DEFAULT_BRANCH`. `lint-helm` is not change-based: it always runs against every `Chart.yaml` found in the repository. `test-java` auto-detects Maven modules via `pom.xml` and runs `mvn test` (override with `JAVA_BUILD`); the linter image does not provide Maven or a JDK, so run it in a Maven/JDK test image (`TEST_IMAGE`). `FILTER` is passed only to Super-Linter.
- `docs/`: `usage.md` explains how to run the linter locally, in CI, and in GitHub Actions. `supported-checks.md` lists Super-Linter enables/disables and the Makefile test / skillcheck targets.

## Rules that are not obvious from the code

- **Rule files are found through a relative `LINTER_RULES_PATH`.** Super-Linter reads rules from `${GITHUB_WORKSPACE}/${LINTER_RULES_PATH}/<file>`, so `run.sh` sets `LINTER_RULES_PATH` to a `../../…` path that climbs out of `/tmp/lint` to the writable work dir. An absolute path would never match and Super-Linter would silently use its own defaults (or fail for custom names like `.checkstyle.xml`).
- **Go module cache lives inside the repository.** The image defaults `GOMODCACHE=/tmp/lint/.go/pkg/mod`, which resolves to the checkout through the `/tmp/lint` link. CI jobs may override it (ci-tools' `.linter-base` and `.test-base` set `$CI_PROJECT_DIR/.go/pkg/mod`) and cache that path with one shared key. `FILTER_REGEX_EXCLUDE` keeps the cache out of the Super-Linter scan. Locally, `templates/common.mk` passes `GOMODCACHE` to the container when set.
- **Super-Linter plus skillcheck.** `make lint` runs Super-Linter and, when `SKILLCHECK_PATTERNS` is set, also runs `skillcheck`.
- **Set `FILTER_REGEX_INCLUDE` to run the full Super-Linter suite on a filtered set of files.** Set `FILTER_REGEX_INCLUDE` to a regex relative to the repo root, for example `make lint FILTER_REGEX_INCLUDE=services/backuper-service/.*`.
- **Super-Linter `RUN_LOCAL=true` is required in CI too.** It only tells Super-Linter that it is not running inside GitHub Actions; GitLab CI and local runs both set it.
- **Image registry and component name:** the CI build workflow reads `.qubership/docker.cfg`. The component is named `linter`, so the published image is `ghcr.io/netcracker/linter`.
- **Entry point behavior:** `Dockerfile` sets `ENTRYPOINT ["/usr/local/bin/run.sh"]` and `CMD ["all"]`. CI workflows disable the entry point with `--entrypoint=""` (GitHub Actions) or `entrypoint: [""]` (GitLab CI) so that `make lint` runs as the container command.
- **kubeconform needs a `.yaml`-suffixed input file.** It filters input files by extension, so `run_helm_lint` renders each chart to `mktemp --suffix=.yaml`, not a plain `mktemp` file — otherwise kubeconform silently reports "0 resource found in 0 file" instead of validating anything.
- **`find` in this image is BusyBox, not GNU findutils.** BusyBox `find <symlink>` does not follow a symlinked starting path unless `-L` is passed, even though the path is the literal argument (GNU `find` would follow it). In CI, `/tmp/lint` is always a symlink (created by `prepare-ci-workspace` or by the fallback block at the top of this script), while locally it is a real bind mount — so `find /tmp/lint ...` without `-L` works locally and silently finds nothing in CI. `run_helm_lint` uses `find -L`. `warn_if_missing_go_proxy`'s `find /tmp/lint -name go.mod` does not and has the same latent gap; not fixed here since it is outside the Helm-lint change.
- **CRD validation uses `openapi2jsonschema`, bundled free with kubeconform's own image — nothing is built from source.** `yannh/kubeconform`'s Dockerfile (driven by its `.goreleaser.yml`, which has a separate `openapi2jsonschema` build alongside `kubeconform`) copies both `/kubeconform` and `/openapi2jsonschema` into `ghcr.io/yannh/kubeconform`. Super-Linter's own Dockerfile only copies `/kubeconform` from that image into its base image, dropping `/openapi2jsonschema`. `linter/Dockerfile` adds a second `COPY --from=` stage against the same pinned `ghcr.io/yannh/kubeconform` image to pick it up (no cloning, no `go build`, no `go install` — the latter does not work anyway, because that repo's `openapi2jsonschema-go/go.mod` declares module path `github.com/yannh/kubeconform/scripts/go`, which does not match where the directory actually lives). `run_helm_lint` runs it against every CRD under `<chart>/crds/` (writes `{kind}_{version}.json` into a scratch dir, since the tool always writes to its current directory) and adds that directory as a `-schema-location` for kubeconform. `-ignore-missing-schemas` stays on as a fallback for any kind that still has no schema anywhere (for example a CRD a chart depends on but does not vendor under its own `crds/`).
- **`value-profiles/` is the standard directory for a chart's deployment value profiles.** `run_helm_lint` looks for `<chart>/value-profiles/*.yaml` (and `.yml`); when present, it runs `helm template -f <profile>` + kubeconform once per profile instead of once with the chart's default `values.yaml`, since defaults alone are often incomplete placeholders. A chart without that directory still gets the single default-values run it always got. The CRD schema directory is generated once per chart and reused across all of that chart's profiles, since schemas do not depend on values.
